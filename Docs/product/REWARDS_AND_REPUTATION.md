# Rewards and reputation

WRS uses multiple progress and value systems. They must remain distinct in language,
storage, and user experience.

## Value types

| Type                | Meaning                                              | Cash value                                      | Example                               |
| ------------------- | ---------------------------------------------------- | ----------------------------------------------- | ------------------------------------- |
| XP                  | progression signal for verified participation        | none                                            | course or accepted training XP        |
| Points              | program score for eligible actions                   | none unless a specific promotion says otherwise | event participation points            |
| Upgrade token/boost | capability entitlement inside WRS                    | none                                            | temporary task-limit boost            |
| Platform credit     | restricted purchasing value under stated terms       | normally non-withdrawable                       | marketplace credit                    |
| Pending money       | a conditional amount not yet settled or withdrawable | not yet                                         | contribution awaiting reconciliation  |
| Confirmed money     | settled monetary balance subject to withdrawal rules | yes                                             | paid service or approved distribution |
| Promotional reward  | time-limited benefit with disclosed terms            | varies                                          | campaign bonus                        |

No exchange rate between XP/points and money should be implied unless a specific,
lawfully reviewed program defines it. Balances use separate ledgers and transaction
histories.

## Reputation systems

### Contributor quality

Reflects accepted work, accuracy, consistency, corrections, task difficulty, and review
history. It unlocks data tasks but is not raised by buying a package.

### Validator trust

Reflects calibrated review quality, agreement with adjudication, false decisions,
appeals, conflicts, and policy conduct.

### Robot reputation

Reflects verified training completion, digital/physical deployment performance,
reliability, safety, and owner-authorized community participation. It must show its
components; one opaque score must not determine unrelated opportunities.

### Community standing

Reflects conduct, completed training, service, and resolved responsibilities. Referral
volume alone cannot establish leadership eligibility.

## Earning rules

Every reward rule specifies the action, verification source, amount/range, limits,
effective dates, reversal conditions, sponsor/budget, and abuse controls. Rewards are
created from immutable events and must be idempotent.

Examples include verified course completion, accepted data, approved event attendance,
valid bug reports, completed community service, or reconciled commercial work. Clicking,
holding a package, or repeatedly generating low-quality volume is not rewardable value.

## Leaderboards

Leaderboards are opt-in, time-bounded, and separated by meaningful category. They avoid
displaying balances, sensitive data, or combined rankings that favor wealth. Quality
thresholds and anti-abuse review apply before publication. Members can use a display
name and hide their position.

## Event codes

Event code rules are defined in the [community leadership specification](COMMUNITY_LEADERSHIP.md).
Claims create a participation event first; the reward service consumes that verified
event exactly once.

## Disputes and reversals

Users can inspect the rule and source event for material rewards. Corrections use
reversal and replacement entries rather than editing history. Monetary disputes,
contribution appeals, and community conduct appeals follow separate workflows.
