# Production readiness review — 8 September 2026

Decision: NO-GO for live release. Local engineering checks pass, but production routes still expose prototype account data and the launch evidence gate remains blocked.

Reviewed checkout: `dbd25716d12029e7712cd70d0237cebd661dc0a8`. This is a local readiness review, not a completed live security or provider audit. No application code or provider configuration was changed.

## Findings

1. **P1 — Notifications display invented account events in production.** `src/screens/Notifications.jsx:58` uses `useMockFetch(notifications)` unconditionally. `src/App.jsx:131` serves this component to authenticated users in every mode. Fixtures include dataset approval, accepted deployment, reward credit and withdrawal review (`src/data/mock.js:939`). Read state is only component memory. The demo banner disappears outside demo (`src/components/AppShell.jsx:291`). Replace this with authenticated server notifications and persisted read state, or an unavailable state until the service exists. Verify that a new production account cannot see fixture events.

2. **P1 — Training and contribution dashboards show fabricated personal progress.** `src/screens/DataQuality.jsx:3` imports a static robot and quality breakdown; its screen shows 94% quality and an Advanced trust level. `src/screens/DataContribution.jsx:74` renders mock statistics plus hard-coded approved/rejected/pending/completed counts. `src/screens/Training.jsx:5` imports mock progress and contribution totals. These routes are mounted without a demo/production component split (`src/App.jsx:109`). Read authoritative per-user summaries or show empty/unavailable states. Test two users with different histories and a new user with no history.

3. **P2 — Normal build success does not establish production configuration.** `src/lib/runtimeConfig.js:21` defaults to demo, and the production assertion returns early for that mode. `npm run build` succeeds without proving that a live configuration was selected. Existing live preflight and launch gates must be required by the actual release path; validate the deployed artifact's mode and candidate. This is a release configuration risk, not evidence of a deployed authentication bypass.

4. **P2 — Local tests leave a production-mode coverage gap.** The browser suite explicitly tests demo labeling and a local demo robot lifecycle. `tests/plan1/mockDataPolicy.test.mjs` tests policy return values, which does not detect the unguarded screens above. Add production-mode rendering checks against controlled API responses and run the existing staging suite against real dedicated infrastructure.

## Recommended order

1. Remove production exposure of mock account progress and notifications; add regression coverage.
2. Refresh the infrastructure evidence and establish a dedicated staging deployment with working API handlers.
3. Run authenticated staging journeys, payment/payout and sensitive-data drills; then recovery, observability, accessibility and mobile performance checks.
4. Obtain the named human approvals and require the strict launch gate before promotion.

The root README is outdated: it describes a UI-only prototype despite the repository containing backend services, migrations and launch controls. Update setup instructions to distinguish demo UI, API-backed development and deployed staging.
